Experimental method and interpretation
- Four HTTP workers, 16 clients, 100 records/request; 320k warmup per restart.
- RSS sampled every 50ms; CPU includes delivery/drain and excludes the 10s idle period.
- Busy RSS is the median of samples in the runner steady window; peak is sampled RSS.
- RSS GiB seconds integrates RSS during measured completion, excluding post-drain idle.
- Null output counters reconcile accepted/completed counts; no per-record ID uniqueness proof.
- Completion and throughput use 1s counter polling. Small differences are not speed guarantees.
- Saturation builds can have different queued work. Matched-rate cases are the cleaner comparison.
- JSON/protobuf ingestion: 30M/run. Modified and 500k/s cases: 10M/run.
- Filesystem saturation: 10M/run. Filesystem 100k/s: 3.2M/run. Mixed-size: 10M/run.
- Mixed-size 100-record batches contain 70x64B,20x512B,9x4096B,1x65536B bodies.
- Rotated build order and 3 restarts; server CPUs 0-3, generator CPUs 4-7,12-15.
- Shared x86_64 Linux host, 4KiB pages, powersave/boost and preexisting swap.
- Swap counters are host-wide; they cannot attribute swapping to a benchmark process.
- Check summary.json for no-swapout sample counts and CPU medians.
- No allocator sampler/Valgrind/LD_PRELOAD in headline timing. MALLOC_CONF cleared except factorial controls.
- Special defaults are bundled-only configure settings; runtime environment overrides were verified.
- No dirty-decay, arena-count, background-thread or page-size tuning was added.
- These finite tests do not certify long-uptime fragmentation, ARM64, musl, or 64KiB kernels.

Mechanism and limits
The factorial control changes options on the same stock 5.4 binary, avoiding a relink confound.
lg_extent_max_active_fit changes dirty-extent selection/splitting and a coalescing bound.
Value 30 is therefore not an exact restoration of all 5.3 policies (whose fit default was also 6).
disable_large_size_classes:false restores large-size-class rounding, potentially leaving realloc headroom.
The tests do not trace realloc moves, so that mechanism remains plausible rather than directly measured.
See bundled jemalloc doc/jemalloc.xml.in:1205,1696 and src/extent.c:454,1052; src/eset.c:281.
Filesystem idle retention must be assessed separately from busy RSS; do not claim complete parity.

Release decision and tradeoffs
Release decision: keep the conservative jemalloc 5.3.0 rollback proposal for 5.2.
This preserves the allocator shipped in 5.1 and its memory budget on existing
workloads. It is not a claim that 5.3.0 is the lowest-RSS or fastest policy in
all workloads. Default 5.4 and fit-only 5.4 have substantial mixed-size wins.

The supplied two-option policy helps the original filesystem case: median busy
RSS falls from 1157.4 to 622.6 MiB, below 5.3.0's 737.6 MiB. It also recovers
matched-rate JSON/protobuf memory. But it is not a universal replacement:
- Saturated protobuf memory: 315.1 MiB vs 290.8 MiB for 5.3.0 (+8.4%).
- Filesystem RSS after 10s idle: 458.9 vs 340.9 MiB for 5.3.0 (+34.6%).
- Mixed-size stress: 6447.5 MiB busy / 11696.7 MiB peak vs default 5.4's
  2324.5 / 3881.9 MiB. CPU cost 3.520 vs 3.239 s/M logs (+8.7%).

The fit-only follow-up retains 5.4 large-allocation rounding and recovers most
filesystem savings (633.7 MiB), while using 1516.7 MiB in mixed-size stress.
That is promising for continued 5.4 work. It still uses 358.1 vs 290.8 MiB in
saturated protobuf (+23.1%) and 92.9 vs 82.7 MiB in matched protobuf (+12.3%).
It has not met the prior release's no material memory increase goal either.

The mixed-size downside of rollback is material: 5.3.0 uses 5513.8 MiB busy,
10989.1 MiB sampled peak and 71.87 RSS GiB seconds, versus default 5.4's
2324.5 MiB, 3881.9 MiB and 22.55 GiB seconds. Completion medians are 12s and
10s. This guard uses batches with 1% 64KiB bodies, 9% 4KiB, 20% 512B and
70% 64B, repeated for 10M records; it is not a long-uptime production trace.
Do not describe rollback as a memory improvement for every user.

In the original filesystem case, fit-only already recovers most of the paired
policy's gain; classes-only does not. The supplied assertion that neither
setting can work alone does not hold for that Fluent Bit workload. This does
not establish whether both options are necessary in other workloads.

These results justify the rollback as a conservative release compatibility
choice, while providing a reason to continue investigating 5.4 and selective
buffer-allocation/reuse behavior. They do not establish a universal best
allocator policy, a single culprit commit, or an in-place realloc mechanism.
No additional arena/decay/background-thread/page-size changes were tested.
